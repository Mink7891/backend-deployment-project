# Нагрузочный тест Game Radar

План `game-radar.jmx` использует только стандартные компоненты JMeter 5.6.3: HTTP,
JSON Extractor, Groovy Assertion/Timer и Thread Group. Дополнительные плагины не нужны.
Запускать генератор нужно на машине сборки, а сервис — на другой машине.

## Сценарий

Каждый виртуальный пользователь один раз создаёт собственный wishlist, затем
добавляет LEGO Batman (`game_id=612`, Steam, порог `5.00`). После этого циклически
читает сводку wishlist и историю цен игры. Получаются четыре операции API, две
из которых записывают данные в PostgreSQL. Проверяются HTTP-коды и смысл JSON:
ID, сохранённая игра, источник `mock`, цена `3.99`, сработавший порог и история.
Ошибка assertion делает запрос неуспешным; пользователь прекращает сценарий.

Тест требует отдельного Compose-проекта с `PRICE_SOURCE=mock`. Цены mock
вымышленные, фиксированные; запросов к CheapShark не происходит. После прогона
тестовый проект и его тома удаляются CI, поэтому рабочие wishlist не затрагиваются.
БД песочницы — `radar_load`, API — порт 8001, отдельные Prometheus/Grafana —
9091/3001. Перед очисткой Jenkins сохраняет метрики нагрузки в
`reports/load-monitoring.json`; dashboard рабочей Grafana на 3000 относится
к production, а не к нагрузочному стеку.

## Ступени нагрузки

`threads` задаёт число пользователей **в одной ступени**, `steps` — число ступеней.
Всего запускается `threads × steps` пользователей. Новая группа начинает запросы
каждые `hold_seconds`; внутри группы старт распределяется на `ramp` секунд.
Задержка задана Timer и не входит в HTTP `elapsed`.
JMeter создаёт потоки заранее, а HTTP-запросы начинаются по расписанию групп.
Для подтверждения ступеней используйте динамику HTTP RPS и время первых
запросов каждой группы; счётчик потоков JMeter включает и ожидающие группы.

При значениях по умолчанию нагрузка растёт примерно так:

| Время | Пользователи |
| --- | --- |
| 0–5 секунд | 0 → 10 |
| 5–30 секунд | 10 |
| 30–35 секунд | 10 → 20 |
| 35–60 секунд | 20 |
| 60–65 секунд | 20 → 30 |
| 65–95 секунд | 30 |

`ramp` должен быть меньше `hold_seconds`. Продолжительность по умолчанию —
`steps × hold_seconds + ramp`; `duration` позволяет явно заменить её. Если
задаёте `duration`, оставьте время для последней ступени. `think_ms=250`
задаёт паузу перед каждым запросом. Количество потоков — заданная нагрузка;
фактические RPS и ошибки берутся из JTL, а не из этой таблицы.

## Запуск non-GUI

Пример для Linux-машины сборки; адрес сервиса и секрет берутся из окружения:

```bash
mkdir -p artifacts
test -n "$API_KEY"
jmeter -n -t load-tests/game-radar.jmx \
  -Jhost="$LOAD_HOST" -Jport="${LOAD_PORT:-8001}" -Jprotocol=http \
  -Japi_key="$API_KEY" -Jthreads=10 -Jsteps=3 -Jramp=5 -Jhold_seconds=30 \
  -Jjmeter.save.saveservice.output_format=csv \
  -Jjmeter.save.saveservice.timestamp_format=ms \
  -l artifacts/results.jtl -e -o artifacts/jmeter-report
python3 load-tests/check_results.py artifacts/results.jtl \
  --max-error-rate 0.01 --p95-ms 1000 > artifacts/load-summary.json
```

JMeter требует новый либо пустой каталог HTML-отчёта. Jenkins архивирует JTL,
HTML и JSON даже при нарушении порогов. Не сохраняйте API-ключ в `.jmx` и логах.

## Порог качества

`check_results.py` не требует сторонних Python-пакетов. Он читает CSV JTL,
считает p90/p95/p99 методом nearest rank, долю ошибок, RPS и количество запросов
по операциям. RPS = число запросов / время от начала первого до завершения
последнего запроса, включая интервалы между запросами.

- Код `0`: ошибки ≤ 1% и p95 ≤ заданного порога.
- Код `1`: ошибки > 1% или p95 > порога.
- Код `2`: пустой, отсутствующий или повреждённый JTL либо некорректные параметры.

Порог p95 `1000 мс` — начальный бюджет: чтение локальных данных должно укладываться
в секунду при максимальной ступени на выбранных учебных VM. Это проектное
требование, пока не подтверждённое замерами. В отчёте укажите CPU/RAM обеих
машин, сетевую задержку, достигнутые RPS, p95 и причины выбора порога. При
пересмотре порога измените параметр Jenkins и обоснование, сохранив старые результаты.

В репозитории находятся план и проверка результатов. Само наличие этих файлов
не доказывает успешный прогон; доказательство — реальный JTL, HTML-отчёт,
графики мониторинга и успешная стадия на двух разных машинах.
